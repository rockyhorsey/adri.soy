Optical flow and occlusion ground truth from 3D renders

Proof of concept for a synthetic-data annotation project · November 2026

TL;DR

  • A Python tool that takes a renderer's standard outputs (multipart EXR with depth and Cryptomatte object IDs, amodal masks, camera and object transforms) and produces forward and backward optical flow with a per-pixel validity mask, the object in front of anything hidden, and each object's visibility history: occlusions, exits, reentries and frames since last seen.
  • Flow is computed from geometry, not estimated from pixels. On a sequence with a moving camera and independently moving objects it matches Blender's own motion-vector pass to 0.00085 px (95th percentile).
  • On the looping orrery below, the independent ray-cast oracle agrees with the tool on every full occlusion of the 14 tracked objects, to within a few frames at two boundaries (listed under "How it was checked"). The tool records why each object is missing, not just that it is missing.
  • RenderA brass orrery with planets on thin arms, moons that pass behind planets, and a coral body that leaves the frame and returns.
  • Forward flowWhere each pixel goes in the next frame. Colour is direction, brightness is speed.
  • Backward flowWhere each pixel of the next frame came from, computed independently.
  • OccludedPixels that will be hidden in the next frame, with the object hiding them.
  • RevealedBackground that a moving object has just uncovered (disoccluded).
  • TimelineEach object's state: visible, occluded (red), out of frame (blue), with event markers.

Why backward flow is computed separately

It is tempting to get backward flow by flipping the forward flow, or by pushing forward vectors onto the next frame. Both look fine on most of the image and fail exactly where the annotations matter: background that a moving object has just revealed. Those pixels did not exist in the previous frame, so no forward vector describes them.

Method, on revealed pixelsResult
Negate the forward flow90% wrong by more than 1 px
Push forward vectors onto the next frame88% get no value
Reproject from the next frame (this tool)Correct, and marked as revealed

Measured on 46 frame pairs with moving cameras and objects; 55,106 revealed pixels.

Brief occlusions vs real exits

A short occlusion and a short exit look the same to a smoothing filter: the object is absent for a frame. Hysteresis turns the occlusion into a fake exit, and gap-bridging deletes both. This tool records why each object is missing before any event is created: hidden by another object (and which one), out of frame, behind the camera, or an unexplained annotation dropout, which is flagged rather than turned into an event. On six synthetic stress cases this got all six exactly right; hysteresis and gap-bridging got three each.

In the loop, the gold eclipse moon passes behind the gold planet across the loop seam (frames 240, 1 and 2), and it is only fully hidden for those frames. The teal eclipse moon is fully hidden behind the central sun for frames 89–153. Each of these is recorded as an occlusion with its occluder, not as an exit, and the independent ray-cast check agrees on the frame ranges.

Limits

  • Objects are assumed to move rigidly with their transforms. A built-in check flags objects that deform, such as characters or cloth, instead of silently producing wrong flow for them.
  • Edge pixels that mix two surfaces are flagged as ambiguous rather than given an exact vector.
  • Transparent, refractive and motion-blurred surfaces need a renderer-specific approach.
